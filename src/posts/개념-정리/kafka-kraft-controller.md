## 브로커와 컨트롤러의 역할

브로커는 파티션의 데이터를 저장하고 프로듀서의 쓰기와 컨슈머의 읽기를 처리한다. 컨트롤러는 브로커의 등록 상태, 토픽과 파티션의 배치, 파티션별 리더 같은 클러스터 메타데이터를 관리한다.

KRaft는 Kafka가 Raft 합의 알고리즘을 이용해 메타데이터를 관리하는 방식이다. Kafka 안에 구현되어 있고, 컨트롤러 역할의 Kafka 프로세스들이 동작을 맡는다. Kafka 4.0부터는 ZooKeeper 방식이 제거되어 KRaft만 지원한다. [Kafka 업그레이드 문서](https://kafka.apache.org/40/getting-started/upgrade/)

같은 Kafka 프로그램을 실행하되 `process.roles`로 역할을 고른다.

| process.roles | 담당 업무 | 프로세스 구성 |
|---|---|---|
| `broker` | 데이터 저장과 클라이언트 요청 처리 | 브로커 전용 JVM |
| `controller` | 메타데이터 관리 | 컨트롤러 전용 JVM |
| `broker,controller` | 두 업무를 함께 수행 | 한 JVM 안에서 두 역할 실행 |

컨트롤러 3대와 브로커 3대를 분리해 실행하면 Kafka JVM 프로세스는 총 6개다. 겸용으로 3개를 실행하면 각 JVM이 브로커이면서 컨트롤러다. 서버 장비의 수와 프로세스 수는 별개다. Kafka 4.2의 [운영 문서](https://kafka.apache.org/42/operations/kraft/)는 중요한 운영 환경에서 브로커와 컨트롤러를 분리하도록 권장한다. 브로커의 부하나 재시작이 컨트롤러에 함께 영향을 주는 것을 피할 수 있다.

## Raft의 대표 선출과 기록 복제

Raft는 여러 서버가 같은 순서의 기록에 합의하도록 하는 알고리즘이다. 대표인 리더를 선출하고, 리더가 받은 변경을 나머지 서버에 복제하며, 확정된 기록을 다음 리더도 유지하게 한다. [Raft 설명](https://raft.github.io/)

KRaft에서 투표권을 가진 컨트롤러들의 집합이 컨트롤러 쿼럼이다. 그중 선출된 리더가 **활성 컨트롤러**가 되고, 다른 컨트롤러는 로그를 복제하며 인계를 준비한다. 브로커 전용 프로세스는 메타데이터를 받아 사용하지만 이 선거에 투표하지 않는다.

컨트롤러 A, B, C 중 A가 활성 컨트롤러인 상황을 가정한다. A가 자신의 임기에 만든 새 변경 기록은 A를 포함한 과반수에 복제되어야 확정할 수 있다.

| 컨트롤러 | 변경 기록 저장 여부 |
|---|---|
| A, 활성 컨트롤러 | 저장 완료 |
| B | 저장 완료 |
| C | 아직 받지 못함 |

3대 중 2대에 저장했으므로 C를 기다리지 않고 확정할 수 있다. C는 나중에 기록을 가져와 따라잡는다. 과반수는 투표 멤버 수를 2로 나눈 몫에 1을 더한 수다. 예를 들어 5대면 `5 / 2`의 몫 2에 1을 더한 3대가 필요하다.

| 투표 멤버 수 | 필요한 과반수 | 진행을 유지하며 견딜 수 있는 장애 |
|---|---|---|
| 3 | 2 | 1대 |
| 5 | 3 | 2대 |

A가 죽으면 남은 멤버들이 다시 투표한다. 후보는 로그의 최신성 조건을 만족해야 하고, 과반수의 표를 얻어야 한다. 기록 복제와 선거 규칙이 함께 확정된 기록을 보호한다. 3대 중 2대가 내려가면 남은 1대는 새 활성 컨트롤러를 선출하거나 메타데이터 변경을 확정할 수 없다.

## 메타데이터 로그와 브로커의 캐시

컨트롤러는 `__cluster_metadata`라는 내부 메타데이터 로그에 변경 기록을 쌓는다. 토픽 생성, 파티션 리더 변경, 브로커 등록 같은 기록을 순서대로 적용하면 현재 클러스터 상태를 구성할 수 있다. 로그가 길어지면 스냅샷으로 상태를 압축해 복구 비용을 줄인다. [컨트롤러 설계](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/158864865/KIP-631+The+Quorum-based+Kafka+Controller)

브로커들도 메타데이터 로그의 확정된 변경을 가져와 자신의 메타데이터 캐시를 갱신한다. 각 브로커는 이 캐시를 이용해 클라이언트에 파티션별 리더와 접속 주소를 알려준다. 브로커마다 반영 시점에는 차이가 있을 수 있다. [KIP-500](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/123898922/KIP-500+Replace+ZooKeeper+with+a+Self-Managed+Metadata+Quorum)은 로그에서 변경분을 가져오는 방식으로 메타데이터 전파를 통일한다.

프로듀서와 컨슈머는 일반적인 메시지 송수신에서 브로커에 메타데이터를 요청한다. 컨트롤러들이 합의한 결과를 브로커를 통해 알게 된다. 프로듀서의 최초 접속과 리더 주소 조회는 [send()의 경로](/posts/kafka-producer-send)에서 다룬다.

## 브로커 장애와 파티션 리더 변경

컨트롤러 A, B, C와 브로커 1, 2, 3이 분리된 구성을 가정한다. A가 활성 컨트롤러이고, 파티션 P3의 리더는 브로커 3이다. 브로커 2에는 새 리더가 될 조건을 만족하는 P3의 복제본이 있다.

1. **브로커 3의 heartbeat가 끊긴다.** 브로커는 활성 컨트롤러에 주기적으로 heartbeat를 보낸다. 브로커 세션 시간이 만료되면 컨트롤러가 장애로 판단한다.
2. **브로커 3을 fenced 상태로 전환한다.** 등록 정보는 남겨 두고 서비스에 참여할 수 있는 대상에서 제외한다. 원격으로 프로세스를 종료하는 동작과는 다르다.
3. **P3의 새 리더로 브로커 2를 결정한다.** 컨트롤러는 복제본의 상태와 선출 정책에 따라 대상을 고른다. 살아 있다는 이유만으로 임의의 브로커를 선택할 수는 없다.
4. **변경을 로그에 기록하고 확정한다.** 컨트롤러 과반수에 복제된 변경을 브로커들이 가져와 반영한다.
5. **복제와 클라이언트 연결이 새 리더를 따른다.** P3의 팔로워는 브로커 2에서 데이터를 가져온다. 클라이언트도 메타데이터를 갱신해 새 리더에 요청한다.

브로커 장애를 감지하는 heartbeat와 메타데이터 로그를 가져오는 요청은 별개다. heartbeat는 생존 여부와 서비스 참여 상태를 관리하고, 로그 조회는 클러스터 상태 변경을 반영한다. [KIP-631](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/158864865/KIP-631+The+Quorum-based+Kafka+Controller)은 두 요청을 구분한다.

## 컨트롤러 선출과 파티션 리더 선출

| 구분 | 활성 컨트롤러 선출 | 파티션 리더 선출 |
|---|---|---|
| 정하는 것 | 메타데이터 관리를 주도할 컨트롤러 | 특정 파티션의 요청을 처리할 복제본 |
| 결정 방식 | 컨트롤러 투표 멤버들의 Raft 선거 | 활성 컨트롤러가 복제본 상태와 정책으로 결정 |
| 결과 | 쿼럼의 활성 컨트롤러 한 대 | 각 파티션의 리더 |

브로커 전용 프로세스인 3이 죽어도 컨트롤러 A는 그대로 일한다. P3의 리더 변경에 컨트롤러 재선출은 필요하지 않다. 반대로 활성 컨트롤러 A가 죽으면 컨트롤러 선거가 필요하지만, 그 이유만으로 정상 브로커에 있는 모든 파티션 리더를 바꾸지는 않는다.

겸용 프로세스가 죽으면 두 역할이 함께 사라진다. 그 프로세스가 활성 컨트롤러이면서 일부 파티션의 리더였다면 컨트롤러 인계와 해당 파티션들의 리더 변경이 모두 필요하다.

메타데이터의 Raft 과반수와 일반 토픽의 복제 조건도 구분해야 한다. `replication.factor`, ISR, `acks`, `min.insync.replicas`는 메시지 데이터의 복제와 쓰기 성공 조건에 관여한다. 이 값들을 바꿔도 컨트롤러 쿼럼의 과반수 조건이 달라지지는 않는다. 데이터 복제의 조건은 [브로커와 복제](/posts/kafka-broker-replication)에서 다룬다.

## ZooKeeper 방식과의 차이

ZooKeeper 방식에서는 `/brokers/ids/3` 같은 ZNode에 브로커 정보를 저장했다. `/`로 구분되는 경로는 ZooKeeper 안의 트리에서 정보를 찾는 주소다. 브로커 세션에 연결된 임시 노드는 세션이 닫히거나 만료되면 사라지고, 컨트롤러는 Watch 이벤트로 변경을 감지했다.

| 관리 작업 | ZooKeeper 방식 | KRaft 방식 |
|---|---|---|
| 활성 컨트롤러 선출 | 브로커들이 `/controller` 임시 노드 생성을 경쟁 | 컨트롤러 투표 멤버들이 Raft로 선출 |
| 메타데이터 저장 | ZooKeeper의 ZNode | Kafka 내부 메타데이터 로그 |
| 브로커 장애 감지 | ZooKeeper 세션 만료 | 활성 컨트롤러가 broker heartbeat 만료 감지 |
| 장애 브로커의 등록 정보 | 임시 노드 삭제 | 등록을 유지하면서 fenced 처리 |
| 브로커에 변경 전파 | 컨트롤러가 변경을 통보 | 브로커가 확정된 로그를 가져와 적용 |

ZooKeeper와 컨트롤러에 나뉘어 있던 상태 관리가 Kafka 내부의 메타데이터 로그를 중심으로 모였다. 컨트롤러가 교체될 때도 다른 컨트롤러가 복제해 둔 기록을 이어 사용한다. 이 구조로 외부 ZooKeeper 클러스터 운영과 별도의 상태 동기화 경로를 줄였다. [KIP-500의 설계 배경](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/123898922/KIP-500+Replace+ZooKeeper+with+a+Self-Managed+Metadata+Quorum)
