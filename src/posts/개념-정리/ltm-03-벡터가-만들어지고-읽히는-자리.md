기억 시스템에서 벡터 검색이 하는 일은 수백 개 기억 중에서 LLM에게 읽힐 다섯 개를 고르는 것이다. 판단은 그 다섯 개를 읽는 LLM이 한다. 이 구분을 놓치면 임베딩 모델을 고르는 기준, threshold를 잡는 기준, 어디에 벡터를 쓰지 않을지 판단하는 기준이 전부 틀어진다.

맥 한 대에 셀프호스팅한 mem0 서버가 그 저장소다. 사실 추출과 중복 판정은 호스트의 `claude -p`가 끝내고, Docker 안의 서버는 임베딩과 저장과 검색만 한다.

## 벡터가 만들어지는 자리

임베딩 모델은 Ollama의 embeddinggemma다. 300M 파라미터, 768차원, 다국어. 호스트에서 Homebrew 서비스로 돌고, Docker 안의 mem0 서버가 `host.docker.internal:11434`로 부른다. 후보 다섯 개를 고르는 일에는 이 크기로 충분했다.

호스트 쪽 스크립트는 텍스트를 보내고 결과를 받을 뿐 벡터를 만지지 않는다. 벡터가 생기는 순간은 셋이다.

| 순간 | 호출 | 서버 동작 |
|---|---|---|
| 저장 | POST /memories | 텍스트를 임베딩해 INSERT |
| 수정 | PUT /memories/{id} | 새 텍스트를 임베딩해 같은 id의 벡터 교체 |
| 검색 | POST /search | 쿼리를 임베딩해 기존 벡터와 비교, 저장 안 함 |

저장과 수정은 `infer=False`다. 사실 추출과 중복 판정은 호스트의 `claude -p`가 이미 끝냈고, 서버는 받은 문장을 그대로 임베딩한다.

## 저장 형태

Postgres의 memories 테이블은 컬럼이 셋이다.

```sql
id       uuid
vector   vector(768)
payload  jsonb
```

기억 텍스트, 프로젝트, 타입, 세션 id, 생성 시각은 전부 payload 안에 있다. 프로젝트별 검색은 이 jsonb에 WHERE를 걸고 그 안에서 벡터 거리로 정렬한다.

인덱스는 둘이다.

- **HNSW, vector_cosine_ops.** 벡터 근사 최근접 탐색.
- **GIN, to_tsvector('simple', payload->>'text_lemmatized').** 키워드 검색.

mem0는 저장 시 텍스트를 표제어로 정규화한 사본을 payload에 함께 넣고, 검색 때 코사인 유사도와 BM25 점수를 섞는다. 두 번째 인덱스는 그 BM25 쪽을 받친다.

### 기억 본문의 언어

BM25가 섞이는 순간 언어가 문제가 된다. 한국어 프롬프트에서 뽑은 기억과 영어 프롬프트에서 뽑은 기억이 섞이면 같은 개념이 키워드로 안 만난다. 표제어 처리기도 영어 기준이다.

그래서 저장 규칙을 하나로 통일했다. **기억 본문은 영어, 식별자는 원문 그대로.** 파일 경로, 함수명, 포트, 에러 문자열, 한국어 제품명은 번역하지 않는다. 추출 프롬프트에 박혀 있고, MCP 도구 설명에도 박혀 있고, 서버 전역 custom_instructions에도 같은 문장이 있다. 검색 쿼리도 영어 명사구로 던진다. 한국어로 물어도 Claude가 영어로 바꿔 검색하고 답은 한국어로 한다.

## 벡터가 읽히는 여섯 자리

같은 POST /search를 쓰지만 목적과 threshold가 다르다.

| 자리 | 쿼리 | top_k | threshold | 상태 |
|---|---|---|---|---|
| UserPromptSubmit 프리페치 | 프롬프트 전문 | 5 | 0.3 | 켜짐 |
| 중복 판정 후보 | 추출된 사실 하나 | 5 | 0.35 | 켜짐 |
| MCP search_memories | Claude가 쓴 영어 명사구 | 5 | 0.2 | 켜짐 |
| 세션 재개 감지 | 고정 문구, type 필터 | 3 | 0.3 | 켜짐 |
| 파일 읽기 전 컨텍스트 | 파일 경로 | 5 | 0.3 | 훅 미연결 |
| Bash 에러 시 | 에러 문자열, anti_pattern 필터 | 3 | 0.3 | 훅 미연결 |

threshold가 자리마다 다른 것은 결과를 읽는 쪽이 다르기 때문이다.

- **중복 판정이 0.35로 가장 엄격하다.** 여기서 후보로 올라가면 LLM이 "합칠까"를 묻는다. 엉뚱한 것이 후보에 들어가면 엉뚱한 병합이 나온다.
- **MCP 검색이 0.2로 가장 느슨하다.** 결과를 읽는 것이 Claude다. 넓게 받아서 컨텍스트 안에서 고르면 된다.
- **프리페치가 0.3, 중간이다.** 사용자가 보지 않는 자동 주입이라 너무 넓으면 컨텍스트만 먹고 너무 좁으면 놓친다.

결과에 찍히는 score와 threshold가 비교하는 값은 같은 값이 아니다. threshold는 내부 코사인 유사도에 걸리고, 표시되는 점수는 하이브리드 정규화를 거친 값이다. 0.27로 표시된 결과가 0.3 threshold를 통과할 수 있으므로, threshold는 표시 점수가 아니라 회수 결과를 보고 잡는다. 점수의 절댓값에 매달릴 이유도 없다. 0.27이든 0.35든 그 다음에 읽는 것이 LLM이다.

## 벡터를 쓰지 않는 두 경로

코퍼스가 통째로 읽을 크기면 벡터를 건너뛴다.

**하루 한 번 도는 메모리 정리는 벡터 검색을 하지 않는다.** 프로젝트 하나의 기억 전체를 GET /memories로 통째로 받아 Claude에게 넘기고, 병합과 삭제 계획을 받는다. 프로젝트당 수십 개면 "비슷한 것 찾기"보다 "전부 읽기"가 정확하다. 서로 관련 없어 보이는 셋이 합쳐서 하나를 말하는 경우는 유사도 검색으로 안 잡히고 전체를 읽어야 보인다. 병합 결과를 PUT으로 쓸 때만 서버가 재임베딩한다.

**세션 시작 타임라인도 벡터 없이 최신순 목록이다.** "최근에 뭘 했나"는 의미 검색이 아니라 시간순 조회다.
