# 파일 배치와 분류

## 파일을 어디에 두나

```
src/posts/
├── <카테고리>/
│   ├── <slug>.md
│   └── images/
│       └── <이미지 파일>
```

| 항목 | 규약 |
|------|------|
| 파일 위치 | `src/posts/<카테고리>/<slug>.md` — 이 경로 밖의 `.md`는 글로 인식되지 않는다 |
| 카테고리 | 폴더명 그대로. 등록할 곳이 따로 없다 |
| 파일명 | `<slug>.md`. 파일명이 곧 URL의 slug가 된다 (`/posts/<slug>`) |
| 날짜 | **파일명에 넣지 않는다.** frontmatter `date`에만 |
| 이미지 | 글이 속한 카테고리 폴더 아래 `images/`. 본문 참조 문법은 [style.md](style.md#이미지-경로) |

### 이름 규칙

공백은 어디에도 쓰지 않는다. slug·폴더명·이미지 파일명 모두 단어 구분은 하이픈이다 (`http-basics`, `개념-정리`). 카테고리는 화면에 표시될 때만 공백으로 바뀐다 (`개념 정리`).

**slug는 전역 유일해야 한다.** URL에 카테고리가 들어가지 않으므로(`/posts/<slug>`), 다른 카테고리에 같은 slug가 있으면 충돌한다.

한 번 공개한 글의 slug나 카테고리 폴더를 바꾸면 **URL이 깨진다.** 옮겨야 한다면 그것까지 감수하는 결정으로 한다.

## 분류 축

글 하나를 놓고 정할 것은 네 가지다. 축마다 답하는 질문이 다르다.

| 축 | 어디에 | 관계 | 답하는 질문 |
|---|---|---|---|
| **카테고리** | 폴더 | 1:1 | 이 글은 어디 서랍에 들어가나 |
| **태그** | `tags` | N:N | 이 글은 무엇에 관한 글인가 |
| **하위 카테고리** | 자동 | — | (태그에서 추론된다. 직접 지정하지 않는다) |
| **시리즈** | `series` | N:N, 순서 있음 | 이 글은 어떤 흐름의 몇 번째인가 |

카테고리는 하나만 고를 수 있고, 태그와 시리즈는 그 경계를 넘는다.

---

### 카테고리

**폴더가 곧 카테고리다.** 새 폴더를 만들면 그게 새 카테고리가 된다.

현재: `개념-정리` · `면접-준비` · `코테` · `트러블-슈팅`

#### 고르는 기준

카테고리는 **글의 성격**이지 주제가 아니다. Kafka 글이라고 "kafka" 카테고리를 만들지 않는다 — 개념을 정리한 글이면 `개념-정리`, 장애를 해결한 기록이면 `트러블-슈팅`이다. 주제는 태그가 담당한다.

새 카테고리를 만드는 건 **기존 넷 중 어디에도 성격이 안 맞을 때만**이다. 카테고리가 늘어날수록 각 서랍이 얇아지고 탐색 축으로서의 의미가 줄어든다.

---

### 태그

주제를 담당한다. 여러 개 달 수 있고, 이게 유일한 다중 분류 수단이다.

#### 원칙

**기존 태그를 최대한 재활용한다.** 태그의 가치는 여러 글을 묶는 데 있는데, 한 글에만 붙은 태그는 아무것도 묶지 못한다.

표기를 흔들지 않는다. `Next.js`와 `nextJs`가 섞이면 다른 태그가 되어 갈라진다. Jekyll에서 이관된 글에 이런 흔들림이 남아 있으니, 새 태그를 달기 전에 기존 태그 목록을 확인한다.

#### 개수

3~5개가 적당하다. 너무 적으면 안 걸리고, 너무 많으면 태그 페이지가 무의미해진다.

---

### 하위 카테고리

**직접 지정하지 않는다.** `src/lib/subcategory-rules.js`의 규칙이 태그를 보고 자동으로 분류한다. `개념-정리` 하나에 글이 100개 넘게 쌓이면서 카테고리만으로는 탐색이 안 돼 생긴 층이다.

#### 새 주제가 생기면

1. 먼저 **기존 태그로 분류되는지 본다.** 대개 된다
2. 안 되면 `subcategory-rules.js`에 규칙 한 줄 추가
3. **우선순위를 재검토한다** — rule 배열은 "더 구체적인 규칙이 앞" 원칙이다. 새 규칙이 기존 글을 엉뚱한 데로 끌고 가지 않는지 확인
4. 작은 카테고리에 억지로 하위 그룹을 만들지 않는다. 빈 규칙(`트러블-슈팅: []`)은 의도된 상태다

우선순위가 왜 까다로운지, 실제로 어떤 충돌이 있었는지는 [`specs/content.md` §7](../specs/content.md#옵션-d의-보완-런타임-하위-카테고리-레이어-2026-04-4차)에 있다.

---

### 시리즈

**순서대로 읽어야 흐름이 이어지는 글 묶음**이다. 카테고리·태그와 완전히 독립이다.

```yaml
series: CDC 도입기
seriesOrder: 2
```

같은 `series` 문자열을 쓰면 자동으로 묶인다. 등록할 곳은 없다.

#### 쓸 때

- `seriesOrder`는 1부터. 빠진 번호가 없게 한다
- **카테고리가 달라도 된다.** 회고는 `트러블-슈팅`에, 설계 정리는 `개념-정리`에 두고 하나의 시리즈로 묶는 식이 오히려 의도된 패턴이다
- 시리즈 이름은 오타를 조심한다. 빌드가 안 잡아주고 1편짜리 시리즈가 조용히 생긴다

#### 시리즈 vs `order`

| | 쓰는 때 |
|---|---|
| `series` | 여러 날에 걸친, 카테고리를 넘나드는 흐름. 글 상세에 이전/다음 네비가 붙는다 |
| `order` | 같은 날 올린 묶음의 목록 표시 순서만. 네비는 안 붙는다 |

**같은 날 올렸어도 흐름이 있으면 `series`가 맞다.** `order`는 목록 정렬만 건드리는 약한 수단이다.

시리즈 글에는 카테고리 이전/다음 네비 대신 시리즈 네비가 나온다. 둘이 같이 나오지는 않는다.

## 정렬 결과

| 목록 | 순서 |
|------|------|
| 글 목록 (전체/카테고리/태그) | `date` 최신순 → 같은 날짜면 `order` 오름차순 → slug 이름순 |
| 시리즈 내부 | `seriesOrder` 오름차순 |
| 카테고리 목록 | 글 수 많은 순 → 이름순 |
| 태그 목록 | 사용 빈도 높은 순 |

`order`가 날짜를 이기지 못하는 이유(한 번 반대로 만들었다가 최신 글이 안 보였다)는 [`specs/content.md` §4](../specs/content.md#4-카테고리태그-인덱싱)에 기록해뒀다.
